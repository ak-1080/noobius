# October 1 staging capacity qualification: thirty players

This qualification used generated, unfunded QA identities against staging only. It did not change production, the public 50-player cap, signup/admission limits, billing, token trading, or owner wallets. The private signing cohorts and raw Cloudflare tails remain in ignored `.wrangler/`; raw tails include client network metadata. The linked reports contain bounded counters and numeric actor indices. A failed report is not a capacity pass even when most movements succeeded.

Ten additional QA players registered through the ordinary signup path in two five-player cohorts. Their [first](2026-10-01-staging-five-cohort-oct1-a.json) and [second](2026-10-01-staging-five-cohort-oct1-b.json) 30-second smokes passed without interruptions and with exact final saves. A subsequent normal signup received HTTP 429, `Too many new centers have been opened on this network in the last 24 hours.` The partial cohort was kept private and no signup limit was bypassed. The 20 prior accounts and ten new accounts were merged offline into a private 30-player returning cohort.

The initial mixed run completed one ordinary service job in each of six rooms before failing. All thirty sockets closed abnormally in room-sized groups within about one second; the runner could not establish whether that began at Cloudflare, the single test machine, or the route between them. The last room also encountered a four-second game-service `ticket-consume` timeout during recovery. No staging room deployment occurred at the moment of that drop. The second run had a slower recovery and peer gap near a scheduled renewal. A later diagnostic identified its reported `foreign peer` as a **probe mistake**: an expired membership legitimately rejoined the shared plaza, but the probe continued to expect that player in a private center. The later full-window repeat no longer reported a foreign peer, but still missed the three-second unexpected-recovery gate. Its slowest actor obtained a ticket in 345 ms and opened a socket in another 185 ms; joining then took 3,310 ms. Its close reason was `Reconnect to continue.`, not the planned-renewal close reason. The final exact-position check did not run because the recovery assertion preceded it; cleanup succeeded, but durable positions from that failed run are unverified.

The final mixed repeat again completed all six ordinary service jobs, but an actor vanished from peers' view during renewal for 5.3 seconds. One actor received the planned `renew` frame; another closed while that room was reconnecting. Ticket fetches took under a second, while joining took multiple seconds. The probe stopped at its in-window five-second peer gate, so the later exact-position check did not run. There were no cleanup errors. This is a real observed continuity failure, not the earlier stale-scene probe error.

The capacity probe now records bounded numeric peer anomalies, updates expected scene rosters after an authoritative rejoin, matches the browser's immediate fresh-ticket reconnect path, and retries an interrupted setup scene release through its existing bounded recovery helper. A subsequent probe revision moves the recovery assertion after final save verification, so runs that reach that assertion can still report exact durability. These changes affect the QA runner only; no game or room Worker was deployed in this investigation. The focused capacity auth/timeline tests passed 20/20, and the changed script passed syntax, `oxlint`, `oxfmt`, and `git diff --check`.

Cloudflare GraphQL analytics was queried for each failed run's measured timestamp window, filtered to the staging Worker names, staging Durable Object namespace, and staging D1 database. For the first 118-second window it reported 17,541 Durable Object invocations, 19,641 D1 rows read, and 5,962 D1 rows written. For the 305-second movement window it reported 58,763 Durable Object invocations, 34,575 D1 rows read, and 14,830 D1 rows written. Its Durable Object statuses included client/response-stream disconnections, but neither window reported an exceeded CPU limit, exceeded memory limit, or fatal internal error in the periodic metrics. These are [adaptive analytics](https://developers.cloudflare.com/durable-objects/observability/metrics-and-analytics/) for staging windows, not test-exclusive invoice amounts; other staging traffic and ingestion/sampling can affect counts. Raw tails remain private.

**Decision:** thirty-player reliability has not passed; do not infer fifty- or five-hundred-player safety or raise the public cap. Earlier repeated twenty-player runs passed, but they do not erase these thirty-player failures. The next qualification should isolate whether simultaneous cross-room closes originate at the single test host or service, measure game-service admission latency around the slow reconnect, then repeat sustained mixed movement/jobs/trades and exact saves from independent clients. A real browser/mobile pass and separate capacity/cost and operational gates remain required. Cloudflare's [Durable Object WebSocket](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) and [state](https://developers.cloudflare.com/durable-objects/api/state/) documentation informs the room design and recovery tests; it cannot certify this application's observed workload by itself.
