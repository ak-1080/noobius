# September 30 staging mixed-capacity qualification

This qualification uses generated QA wallets, ordinary staging signup and admission, and returning saved accounts. No owner wallet, real token, production deployment, billing setting, or public cap was changed. The private signing cohort and raw Cloudflare tail remain ignored under `.wrangler/`; the linked reports omit signing material and client network metadata. The public cap is still 50, **not** a tested-safe recommendation.

The room startup recovery repair was merged to `main` at `773ef904a239115bebfac142216b39cd1284d76d` and deployed only to the staging room Worker as version `328a5db6-563d-41ff-a7a5-0aec7c4623ce`. It removes game-service network requests from the Durable Object startup concurrency gate. A controlled five-player redeploy recovered in 1.66 seconds, but that controlled replacement did not explain the earlier spontaneous code-1006 closes.

An additional five-player cohort was created through normal staging signup and passed its 30-second smoke with all five final positions saved. It was merged offline with three existing five-player QA cohorts to make 20 distinct returning accounts. No signup limit was bypassed.

The 15-player runs crossed planned room renewals and had no unplanned interruption. In the 20-player run, all five sockets in one room closed with code 1006 within two milliseconds at about 32 seconds, before their authority expired. The first five reconnection handshakes then stalled and failed at the client's eight-second timeout; a second attempt rejoined. The other rooms continued. The run completed all four real service jobs and the planned renewals, but its success counters do not override the failed room recovery. Teardown had no cleanup errors. The harness failed before its final exact-save assertion, so durable positions from this run are **not** certified.

The private room tail at the same time shows one Durable Object alarm invocation with 11.3 seconds of wall time and approximately zero reported CPU time. Five reconnect upgrade requests to that same room waited roughly 7.9–9.2 seconds and ended canceled. A later `room-alarm-late` event in that room measured a 6.1-second delay. No application exception or `room-alarm-slow`/`room-recovery-slow` event appeared. These observations establish a room-wide stall, but do not yet distinguish a storage input gate, Cloudflare runtime behavior, or another awaited dependency. Alarm wall time can include `waitUntil` activity without proving the JavaScript handler blocked; [Cloudflare documents this distinction](https://developers.cloudflare.com/durable-objects/api/state/#waituntil) and [Durable Object input gates](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/#understand-how-input-and-output-gates-work). Raw tail output stays private because it includes client network metadata.

The movement-only repeat admitted the same 20 returning accounts into four rooms, crossed 20 planned renewals, had no unplanned interruption, and saved all 20 exact final positions. Its longest planned renewal and sampled peer gap were 909 ms and 908 ms. This clean run does **not** prove that jobs caused the previous stall: the earlier 15-player mixed run passed, and the outage has been intermittent.

Staging room version `22533d83-3bea-4240-a11b-e7f28e3b1d24` emits fixed-schema begin/complete timing markers for alarms, orphan scans, upgrades and game-service calls. These markers are staging-only and reveal no player identity; the raw tail still remains private. A 20-player mixed run with delayed jobs reproduced the failure against this version. The diagnostic instrumentation is not a repair.

That diagnostic run reproduced a **7,747 ms** room-wide recovery at about 254 seconds, before the delayed jobs began. All five affected clients got code 1006 at the same moment; other rooms continued. Private Cloudflare logs show five `room-socket-closed` code-1006 callbacks in one room and five `authority-release` calls beginning. The next alarm invocation spent 6.6 seconds in wall time with nearly zero CPU and no `room-alarm-trace` begin marker. This suggests dispatch was delayed before the JavaScript alarm handler, but it does not establish why the sockets closed or whether a storage gate, runtime, or network path delayed the event. A five-minute object restart was not observed in the redacted restore markers. The run is a failure regardless of subsequent recovery.

The diagnostic run also exposed a harness reporting bug: its failure-report catch block referenced a `measuredAt` variable scoped inside the `try`, so it threw a `ReferenceError` instead of writing a full JSON report. Cleanup still ran, but exact final saves and job completion were not reported and must **not** be inferred. The variable was moved to shared scope, and a no-network injected health failure now proves that a failed run writes a bounded report with clean cleanup. The private console and tail are retained; no fabricated report was added to this directory.

The close handler still awaited a storage read and a game-service `authority-release` after removing a dead socket. This was unnecessary handler latency: a grant-specific release can complete in `ctx.waitUntil`, while the persisted outbox continues to prevent releasing a grant with an uncertain checkpoint. The handler now returns promptly and records a bounded deferred-release event if storage or service fails. A local regression holds the release request unresolved and confirms that the close handler and a subsequent alarm can finish. This targets **reconnection delay after a drop**, not the initiating code-1006 closure. Staging room version `84d099cb-b2b9-48e5-8ce4-c8de163c9bf3` carries that mitigation and the temporary timing markers. Do not treat its deployment as capacity acceptance.

The first [20-player run after that deploy](2026-10-01-staging-twenty-harness-active-job.json) stopped after only 1.5 measured seconds because the reusable QA accounts already held accepted service offers from the interrupted prior diagnostic; accepting the same offer again correctly returned HTTP 400. It reported zero room interruptions and clean cleanup, but it is **not** a capacity test pass. The harness now resumes an accepted, unstarted service job. The five-player hosted validation completed that job with exact saves and clean cleanup.

That subsequent mixed run failed for a **different** reason. Around 30 measured seconds, room-service calls from multiple neighborhoods timed out after four seconds, one authority refresh returned HTTP 503, and clients in all four rooms lost their short movement authority; some were closed with code 1008 as stale. The [redacted report](2026-10-01-staging-twenty-broad-interruption.json) records 20 interruption callbacks, a 20.8-second sampled peer gap and clean cleanup, but no final exact-save check. The private room tail contains seven authority-refresh timeouts, four movement-checkpoint timeouts, five authority-release timeouts, five connection failures, and no recorded room Worker exception. A later read-only game health request returned HTTP 200 in 193 ms, showing the problem was transient. This run does not validate the close-handler mitigation or establish why the game service stalled.

A 20-player movement-only repeat with **both** Worker tails passed for 371 measured seconds, including 20 planned renewals, no unplanned interruption, 45,463/45,500 accepted movements, 20 exact final positions, and clean cleanup. Its longest planned renewal was 620 ms. The private game Worker tail captured 1,469 `/api/noobius-room` requests, all HTTP 200, with no exception and a maximum reported wall time of 773 ms; the private room tail reported no exception. These are observations from a healthy run, not a reproduction or explanation of the earlier cross-room timeout. The raw tails remain private because they contain client network metadata and signed headers. A clean movement run also does not establish that the mixed job path is reliable.

An immediate mixed-workload retry reproduced the five-client code-1006 drop in one room, six measured seconds into the run. The active job received the room's temporary recovery error, so the strict harness stopped; it did **not** measure how long this specific drop would have taken to recover, complete jobs, or save final positions. The game Worker tail captured 168 room-service requests, all HTTP 200 with maximum reported wall time 578 ms and no exception, so this reproduction does not support the game-service timeout as the trigger. The affected Durable Object had reported five attached sockets on its previous alarm, then a new constructor/restore logged **zero** attached sockets shortly after the group drop. No room Worker exception or deployment was observed during the run. This is consistent with a Durable Object instance shutdown that terminated its WebSockets, but the available logs do not prove *why* it shut down. [Cloudflare's lifecycle documentation](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/#shutdown-behavior) explicitly states that runtime shutdowns can occur and terminate WebSocket connections. The game must recover from this event; a promise that sockets never drop is not a valid acceptance criterion.

The QA job runner now waits for a room reconnect and reuses the same action request ID if a work step is interrupted, refreshing its saved profile and replanning a worksite walk from the restored position. The next 20-player mixed run passed for 372 measured seconds with four completed jobs, 19 planned renewals, one unexpected single-socket interruption recovered in 1,673 ms, all 20 final positions exact, and clean cleanup. Its game tail captured 1,459 room-service HTTP 200 responses, none slower than 787 ms; no game exception was recorded. The unexpected drop occurred after the four jobs finished, so this pass **does not yet exercise** the new in-job retry path or prove that the prior five-socket group reset is harmless. The run's three-second recovery gate remained active.

The near-50 and hundreds-player claims remain premature. Next qualification must allow a job to pause safely during a room reset, measure reconnection and saved state without treating every socket close as fatal, and still reject slow recovery or lost work. Separately, reproduce the cross-room game-service timeout with a game Worker tail active. Repeat sustained mixed jobs, devnet trade/reconnect/save checks, real browser and geographic runners, and Cloudflare Worker/Durable Object/D1 usage measured over the exact test window. A rolling D1 insights view does not give isolated test cost. Both Noobius scheduled checks remain paused at the owner's request.
