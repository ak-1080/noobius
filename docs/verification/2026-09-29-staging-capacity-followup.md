# September 29 capacity follow-up: 15 returning staging players

This work tests the current September 29 staging game and room Workers with generated QA wallets. It does not change production or certify the public 50-player cap. The private signing files are ignored under `.wrangler/capacity-cohorts/`; the committed reports contain no signing keys.

Two additional five-player cohorts were enrolled through ordinary staging signup and passed their 30-second setup probes. They were merged offline with the earlier five-player cohort, yielding 15 registered returning players. No account limit was bypassed. A simultaneous ordinary gameplay attempt was rejected before any gameplay action with HTTP 429: `Too many new centers have been opened on this network in the last 24 hours. Existing centers can still sign in.` Its [report](2026-09-29-staging-gameplay-overlap-signup-limited.json) records the blocked overlap. These runs therefore tested movement, profile reads, room renewal, peer visibility and final saves, **not** a mixed jobs/trades workload.

The first [15-player, six-minute run](2026-09-29-staging-fifteen-slow-recovery.json) had 32,365/32,406 moves accepted, 10 planned renewals, 20 unexpected interruption callbacks, and all 15 final positions saved. At 23:33:01 UTC, five sockets in one room closed abnormally together and took up to **22,943 ms** to recover. At 23:35:34 UTC, five sockets in another room closed together and took up to **9,087 ms** to recover. The report's old `status: passed` reflects an insufficient acceptance rule: it checked eventual recovery and sampled peer rosters, but placed no ceiling on unexpected recovery time. Treat this run as a **capacity qualification failure**. Its 765 ms maximum sampled peer gap does not erase the room-wide transport outage.

Private Cloudflare room-tail output from the latter incident showed a Durable Object alarm with 8,607 ms wall time and zero reported CPU time immediately as the five sockets dropped, followed by five reconnections. The tail also contained canceled requests/stream disconnects and no application exception. This correlation suggests an asynchronous stall or object interruption, but it does **not** establish whether D1, Durable Object runtime, network, or another dependency initiated the problem. Raw tail files stay ignored because request metadata includes client network information.

The harness now fails if an unexpected interruption takes over three seconds to recover. A controlled [repeat with that gate](2026-09-29-staging-fifteen-repeat.json) passed: 34,463/34,486 moves accepted over 372 measured seconds, 15 planned renewals, zero unexpected interruptions, 1,381 ms longest planned renewal recovery and sampled peer gap, all 15 exact final positions saved, and no cleanup errors. Both runs used three five-player neighborhoods from one network location. A clean repeat does not cancel the intermittent failure.

An additional [diagnostic six-minute run on September 30](2026-09-30-staging-fifteen-diagnostic.json) used the same returning cohort with socket diagnostics and a live private room tail from the start. It passed the stricter gate: 34,286/34,325 moves accepted, 15 planned renewals, zero unexpected interruptions, 561 ms maximum planned renewal recovery, 575 ms maximum sampled peer gap, all 15 positions saved, and clean cleanup. The tail recorded 26 `canceled` outcomes but no application exceptions or group-wide stream disconnects. Since those canceled outcomes also occur during a clean run, they alone do not identify the earlier outage's cause. The intermittent fault remains open; do not count three trials with one bad result as a reliable capacity certification.

The September 30 tail review found no slow game-service event at either abnormal group close. The eight-second failed reconnect handshakes account for much of the measured 22.9-second recovery, but do not explain why the whole room became unreachable. Alarm wall time includes work scheduled with `waitUntil` and therefore is not proof that the alarm handler itself blocked. To separate these cases, staging room Worker `1ebf072e-20fb-4f43-a679-37fed8d86585` now emits redacted `room-alarm-slow` and `room-recovery-slow` events for operations lasting at least two seconds. The events contain only bounded duration and socket count (or a fixed `scan` label), never player identities or request metadata. This is instrumentation, not a reliability repair; a recurrence with a private tail is still needed to classify the failure. All 572 rule tests and TypeScript checks passed. Production and its cap were unchanged.

The [first six-minute run after instrumentation](2026-09-30-staging-fifteen-instrumented.json) passed: 34,141/34,169 moves accepted, 15 planned renewals, no unexpected interruptions, 597 ms longest planned renewal recovery, 594 ms maximum sampled peer gap, zero unresolved gaps, all 15 positions saved and clean cleanup. It ran 368.8 measured seconds. Its private tail recorded 1,332 events, including 26 `canceled` outcomes and three alarm wall times of 3.0–3.7 seconds during final teardown; neither new slow-handler nor slow-recovery event fired. This clean run does not reproduce the intermittent outage or identify its cause. A one-hour **rolling** staging D1 insight snapshot after the run showed 12,043 executions, 36,328 rows read, 15,909 rows written and 4.28 seconds summed SQL time across its top 20 query groups. That hour includes other activity, is not an isolated test cost, and excludes D1 queue wait and Worker/Durable Object billing. Full usage and near-50 mixed-workload evidence remain open.

One-hour staging D1 insights were captured privately during and after the trials. The top 20 query groups in the later rolling window reported 28,555 executions, 84,017 rows read, 31,654 rows written and 12.3 seconds summed SQL execution time. That rolling hour includes both runs and other activity, covers only the top query groups, and omits D1 queue wait, Durable Object usage and billable Worker totals. It cannot establish isolated per-player cost.

Next: classify and repair the group-wide room stalls, then repeat longer 15-player runs under the stricter gate. As normal staging signup slots reopen, expand the private returning cohort and run sustained near-50 movement **alongside** ordinary jobs and devnet trade checks, including reconnect and final saves. Measure actual Cloudflare Worker, Durable Object and D1 usage over the test interval before recommending an admission cap. The daily `noobius-staging-capacity-qualification` heartbeat continues this work without owner wallets or production load. Keep the public cap and production deployment unchanged meanwhile.
