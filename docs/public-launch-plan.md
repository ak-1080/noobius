# Noobius public launch plan

Prepared September 7, 2026. This is a release plan, not a production certification. It reflects a read-only inspection of `/Users/main/Documents/ChatGPT/Noobius 2` at commit `1e42db7` plus files present during active development. The major game expansion is being built concurrently; none of its planned features are counted as finished here. Reconcile this checklist against the final release commit before opening access.

The recommended first public release is a free game with saved, nontransferable credits and clearly stated beta status. Real-value rewards are a separate, optional release. Public access does not depend on launching a token.

## How to use this plan

- **P0:** blocks the named release gate. **P1:** required before expanding beyond that gate, or before enabling the named optional feature. **P2:** improvement after the first controlled launch.
- **Done:** the narrow implementation is visible in source. This does not mean its production behavior was independently verified. **Partial:** some implementation exists, but acceptance evidence or required coverage is missing. **Not started:** no implementation or artifact was found in the inspected scope. **Unknown:** requires account, production, commercial, or user evidence unavailable in this review.
- **Engineering** can implement code, migrations, tests, documentation, performance work, and operational tooling. **QA** validates devices and adversarial cases. **Operator** controls hosting, billing, deployment, restore, and incidents. **Product owner** chooses audience, economics, policy, and launch timing. **Community** operates support/moderation. **Counsel/finance** provides jurisdiction-specific legal, tax, and funding decisions. One person can hold several roles, but each gate needs a named person.
- Each unchecked item has a priority, status, owner type, dependency, and measurable acceptance condition. Attach evidence such as a release SHA, test report, dashboard capture, restore log, or signed decision to close it. A README claim alone does not close a production gate.
- All numeric targets below are proposed starting acceptance targets, not measured results or guarantees. Approve or change them before testing; do not lower them after a failed test merely to declare success.

## Release stages and gates

| Gate | Audience and economics | Required evidence to advance |
|---|---|---|
| G0 — Private alpha | Owner/developers; disposable test identities; no payouts | Expansion completes its core loop; migration rehearsal preserves old profiles; all P0 security/integrity failures fixed; temporary practice cannot become trusted saved progress. |
| G1 — Closed beta | Invite-controlled cohort, initially 20–50 people; saved game credits only | A1–A5, B1–B5, C1–C5, E1–E4, F1–F6 pass; supported real wallets tested; restore and rollback drills completed; reporting/moderation works for every enabled social feature. Run at least seven days with enough activity to include 100 completed saved sessions. |
| G2 — Public beta | Anonymous visitors can reach the game; controlled admission if capacity requires it; no redemption | All G1 failures resolved; public access proven from unrelated devices/accounts; load envelope proven at twice launch forecast; privacy/terms/support/brand checks closed; seven-day crash-free session rate ≥99%, no unexplained balance discrepancies, no unresolved P0 defects. Publish known limitations. |
| G3 — Wider public release | Increase audience gradually rather than all at once | Two weeks of stable G2 operation; ≥99.5% crash-free sessions, availability target met, real device performance budget met, queue/support load within staffed capacity, restoration re-tested after material schema changes. Product owner accepts onboarding and retention evidence, not wallet counts alone. |
| G4 — Optional real-value P2E/token pilot | Separately approved eligible cohort; capped, pre-funded payouts | All R items pass; independent security review of the exact payout build/contracts; legal/finance/vendor decisions documented; testnet dry run and bounded live pilot reconcile perfectly. Do not map old credits into claims without an explicit new program. |

Gate counts/durations are provisional planning targets. A seven-day beta with two users is insufficient evidence, and a large bot-generated wallet count is not adoption. An optional item such as QR pairing, smart-account login, or chat can be closed for a gate by recording that it is excluded, disabling it, and publishing the narrower supported scope; do not mark its implementation Done. Disable incomplete optional chat/trading/rewards to pass the game gate only if the released UI and documentation truthfully reflect the narrower scope.

## B. Wallet authentication and API boundaries

- [ ] **B1 · P0 for G1 · Partial · Engineering · Depends: D2, A3.** Resolve address-versus-chain identity. Current nonce accepts any positive safe-integer `chainId`, while players and sessions store only a lowercased address. Decide whether an EOA has one cross-EVM game profile or profiles keyed by chain/address. Persist enough SIWE/session context to enforce the policy, select supported chain IDs, and document future migration. **Pass:** same-address/different-chain tests follow the chosen policy; unsupported chains fail clearly; contract identities are never silently conflated across chains. SIWE explicitly includes chain context, including contract-account resolution. [SIWE specification](https://eips.ethereum.org/EIPS/eip-4361)
- [ ] **B2 · P0 for G1 · Partial · Engineering + QA · Depends: B1.** Harden and test the complete session lifecycle: nonce expiry, simultaneous nonce consumption, wrong account/signature/domain, chain/account switching during signing and after reload, seven-day expiry, logout, revoked sessions, and two tabs changing accounts. Decide maximum sessions per account and an all-sessions-revoke mechanism. **Pass:** every invalid/replayed attempt fails; one challenge creates at most one session; no stale tab mutates another identity; production cookies are Secure/HttpOnly with intended SameSite scope; logout actually invalidates the server token. Never log raw signatures, nonce cookies, session tokens, or keys.
- [ ] **B3 · P0 for G1 · Partial · QA + engineering · Depends: A3, B2.** Run the installed wallet UI, not just a mock provider or local private-key signer. Matrix: Chrome + MetaMask; a second claimed desktop provider; iOS wallet browser; Android wallet browser; no extension; multiple injected wallets; locked wallet; rejected signature; account switch; slow/cancelled handoff; fresh and returning browser sessions. **Pass:** each advertised combination completes login → repair → upgrade → reload → logout with correct balances, no chain transaction or token approval request, and documented wallet/browser versions. User testing supplies their wallet interaction where automation cannot; no funds are needed for login tests.
- [ ] **B4 · P1 for broader mobile; P0 if QR advertised · Not started · Engineering + vendor owner · Depends: B1, D3.** If mobile Safari/Chrome outside wallet browsers must work, add a supported wallet-connection transport/SDK with verified domain metadata, project configuration, app/deep-link return behavior, timeout and stale-pairing recovery. **Pass:** desktop QR pairing and mobile app switching work on real iOS/Android; disconnect clears pairing state; vendor credentials, pricing, and permitted domains are documented. If deferred, clearly state wallet-browser-only support and keep practice immediately available.
- [ ] **B5 · P1; P0 if smart accounts advertised · Not started · Engineering + security · Depends: B1, B4 if used.** Implement chain-specific contract signature verification and supported account abstraction cases, or explicitly limit support to EOAs. Current 65-byte signature regex and standalone message recovery do not cover contract wallets. **Pass:** valid/invalid contract signatures, RPC outage, wrong chain, changed owners, and deployed/undeployed-account scope produce secure documented results; sessions react to relevant ownership changes. Do not require every possible contract-account standard before an honestly labeled EOA beta. [ERC-1271 contract validation](https://eips.ethereum.org/EIPS/eip-1271)
- [ ] **B6 · P0 for G2 · Partial · Engineering + security QA · Depends: B2, final API set.** Inventory every GET/POST/new multiplayer route and apply authorization, body/type/range limits, safe errors, parameterized queries, origin/CSRF protection, and trusted-proxy handling. Add and verify CSP, framing protection, referrer policy, and narrowly scoped browser permissions without breaking wallet providers or WebGL. **Pass:** a negative-test matrix includes malformed JSON, oversized/chunked body, wrong method, unsupported fields, unauthenticated access, cross-account IDs, origin spoof cases, stored-name/chat XSS, and dependency audit triage. No unexplained severe vulnerability remains; final HTML and API response headers are inspected on the hosted build.

## C. Persistent game economy, migration, abuse, and capacity

- [ ] **C1 · P0 for G0/G1 · Partial · Engineering + QA · Depends: final expansion schema.** Version the expanded save format and SQL schema. - [ ] **C2 · P0 for G1 · Partial · Engineering · Depends: C1.** Make the server authoritative for new crafting, building, inventory, quests, daily rewards, milestones, and future trading. Add an auditable append-only economy event/ledger model for grants/spends, with cause, actor, rule version, idempotency key, and before/after or reconstructable totals. **Pass:** reconciliation reconstructs every test account's balance/inventory; negative balances, double ownership, impossible item counts, and reward-after-reset paths fail; client-supplied XP/prices/time/success flags never control saved awards. Current conditional updates are a useful base, not evidence that expansion mutations are safe.
- [ ] **C3 · P0 for G1 · Partial · Engineering + QA · Depends: C2.** Extend idempotency beyond repair answers. Bind each mutation key to authenticated actor, action, and payload fingerprint; retries must return the original result or a clear conflict. Specify retention and transaction boundaries. **Pass:** parallel/reordered/retried requests, disconnect after server commit, two tabs, duplicate purchases, concurrent daily claims, and same-key/different-payload tests produce one logical effect. At minimum run 100 simultaneous identical claims and mixed competing spends against staging; balances and inventory reconcile exactly after failures.
- [ ] **C4 · P0 for G2; stronger requirement for G4 · Partial · Engineering + product owner · Depends: C2.** Write an abuse model for replay, scripted solving, browser clock changes, rapid account creation, multi-account farming, collusion, and leaderboard spam. Current returned puzzle data includes solutions and existing tests read them; random puzzles and a one-second delay are not human verification. Remove unnecessarily disclosed hidden answers, use server challenge/state constraints, and separate suspicion signals from automatic punishment. **Pass:** a scripted abuse exercise documents what remains automatable; scores/awards obey rate and eligibility rules; suspicious rankings can be withheld/reviewed with appeal. Game-only beta may accept bounded bots explicitly. Real-value eligibility cannot rely on current puzzle completion or one-wallet-equals-one-person assumptions.
- [ ] **C5 · P0 for G2 · Partial · Engineering + operator · Depends: A1, C4.** Redesign abuse/cost limits around per-IP, session, wallet, action, and global admission budgets. GET `profile`/`leaderboard` currently bypass the limiter; POST limits write to D1 per request; expired-row cleanup runs randomly. Cover read floods, auth floods, shared-NAT users, IPv6 changes, forged proxy headers, and account rotation. Use edge controls where managed hosting exposes them and deterministic bounded cleanup. **Pass:** attacks return graceful 429/503 with retry guidance before exhausting paid resources; legitimate same-network players still function; cleanup age is measurable; leaderboard/public reads are cached safely or cost-bounded; auth and private profile responses are never shared in cache.
- [ ] **C6 · P0 for G2 · Not started as capacity evidence · Engineering + QA + operator · Depends: C1–C5, M1 if enabled.** Create a workload model in actions/second, database operations, presence traffic, payload bytes, and rows/day. Test 25 → 100 → 250 concurrent simulated players, or higher if twice the approved launch forecast; use realistic think times plus a burst at twice the sustained target. Run 60 minutes sustained, 10 minutes burst, and recovery from a DB/RPC outage. **Pass:** API p95 <500 ms and p99 <1.5 s under target load, unexpected 5xx <0.5%, no corruption/lost awards, acceptable 409 retry recovery, and no growth in queues/memory after load subsides. Record max safe admission and fail below it rather than inventing “unlimited players.” D1 database throughput depends on query duration; each database processes queries serially. [D1 limits and throughput](https://developers.cloudflare.com/d1/platform/limits/)
- [ ] **C7 · P1 for broader public launch · Not started · Product owner + engineering + QA · Depends: C2.** Simulate progression rather than tuning solely from a feature list: time to first upgrade, income/spend balance, capped items, endgame usefulness, daily boundary behavior, resets/seasons, inactive returns, and new-vs-veteran advantage. **Pass:** representative new/casual/intensive/scripted profiles have no unavoidable progression deadlock; time-to-goal targets are written before beta; telemetry and playtests explain outliers; live rule changes are versioned and never silently erase purchases. Distinguish engagement goals from financial yield promises.

## R. Separate gate for any real-value rewards, token, or NBIS exposure

Keep these items out of the public game launch's critical path unless the owner explicitly changes the release scope. None is presently done. They apply before paid entry tied to prizes, redeemability, tradable reward issuance, cash-outs, token distribution, or financial marketing is enabled—not merely before a particular “token launch” label.

## Launch-day checklist

- [ ] **Operator:** freeze unrelated changes; record final SHA, schema, settings, current recovery bookmark/export, and previous build. Confirm operator and backup are reachable.
- [ ] **Engineering + QA:** run the release checks against staging and smoke-test production read-only behavior; confirm test accounts/data are excluded from public rankings and analytics where intended.
- [ ] **Operator:** verify billing/quotas, dashboards, synthetic uptime/login check, cost alerts, admission cap, and feature/write-disable controls. Test alert delivery one last time.
- [ ] **Product owner:** record the go/no-go decision, declared beta scope, and any accepted P1 limitations. No unresolved P0 can be accepted silently.
- [ ] **Operator:** make the prepared supported audience-policy transition to public. Do not broaden admin roles or secret access as part of opening the game.
- [ ] **QA:** from a fresh unrelated browser on cellular data, load the landing, enter practice, sign with a supported wallet, complete a repair, save/reload, and disconnect. Confirm profile data is private and origin/cookies are correct.
- [ ] **QA + community:** test report/support/help links and enabled chat controls; verify public metadata/preview images and all official URLs.
- [ ] **Community owner:** publish the prepared release announcement through approved official channels only after public smoke tests pass; state beta, known limitations, supported wallets, and absence of a live reward/token program where applicable.
- [ ] **Operator + engineering:** watch the first 15 minutes, then each hour during the staffed launch window: login conversion/failures, API latency/5xx/429/409, D1 usage, balance invariants, active rooms, crashes, and cost run-rate.
- [ ] **Incident commander:** stop admission or disable the affected feature if unexpected 5xx exceeds 2% for five minutes, legitimate login failures exceed 10% of attempts for ten minutes, balances fail reconciliation, a material data exposure appears, or burn exceeds the approved daily cap. Use sample-size/context checks; a single failed login is not an outage. Data corruption or exposure warrants immediate containment without waiting for a traffic threshold.
- [ ] **Operator:** rollback the application only where schema compatibility is proven; freeze affected writes and follow the restoration runbook for data problems. Record precisely what changed and whether player state was lost.
- [ ] **Community + operator:** close the launch window with a concise status, known-issue ownership, next on-call handoff, and the next review time.

- [ ] **Days 2–7:** review funnel dropoffs, legitimate rate-limit friction, suspected bot clusters, mobile wallet failures, moderation response times, save recovery and churn. Fix the highest observed issues before increasing acquisition.
